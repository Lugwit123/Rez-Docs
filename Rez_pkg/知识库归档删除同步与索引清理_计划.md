# 知识库归档的"删除同步"与索引清理（计划）

> 状态：**索引侧已实施**（2026-10-04；§4 步骤 A/C 到位并实测，含清旧行的**向量侧**收尾 —— 见 §2.3 §2.4 §5）。
> 步骤 B（同步器传播删除）**不做**：多台机器各有工作区，本地没有某文件 ≠ 该从共享归档删掉它（见 §6）。
> 相关：`Rez-Docs/Rez_pkg/笔记元数据与notepad工具改造_计划.md`（删除前先读 `meta.note`）；
> 本议题属 `l_notepad_server` + `lugwit_baidu_netdisk`。

---

## 1. 现象（谁都能复现）

`Rez-Docs/` 被当成知识库工作区（kb `rez_pkg`）实时同步进版本库，索引读的是**版本库归档**。
2026-10-04 重整合并文档后：

```bash
# 搜已删的文档，仍能命中，而且分数最高
curl -s -G "http://127.0.0.1:8765/api/search" --data-urlencode "q=多实例与迁移_手册" --data "limit=6"
#  → rez_pkg | Rez_pkg/wuwo_多实例与迁移_手册.md | 96.4   ← 文件早已从 Rez-Docs 删除
```

而新文件能正常命中 → **同步/索引只增改、不消灭**。

## 2. 根因（已用接口实测，不是推断）

### 2.1 归档列举**仍返回**该文件，且带着状态字段

`GET /api/kb/rez_pkg/depot/list?rel=Rez_pkg`（33 项）里它还在：

```
wuwo_多实例与迁移_手册.md | action = add | pending = (空) | excluded = False | rev = 1
ayon.md                   | action = add | excluded = False | rev = 1      ← 正常
l_tray.md                 | action = edit| excluded = False | rev = 12     ← 正常
```

**注意：它的 `action` 是 `add`，不是 `delete`** —— 说明**归档从没收到过"删除"这件事**。

### 2.2 两层各自的问题

| 层 | 位置 | 问题 |
|---|---|---|
| 同步器 | `l_notepad_server/workspace_sync.py::_scan_kb` | 只调 `depot_map.submit_file`（增/改）；**没有任何删除分支**。源端文件消失后，`_synced` 状态里还留着它，归档也照旧 |
| 归档映射 | `l_notepad_server/depot_map.py::list_tree` | 只取 `rel/path/name/size/rev`，**把 `action` / `pending` / `excluded` 全丢了** → 消费者（索引）无法区分"活文件"与"已删状态" |
| 索引 | `l_notepad_server/search_index.py` | 按 `list_tree` 的结果建/更新行；文件从列举消失时**不会删行** |

### 2.3 实测更正（2026-10-04，做完显式标删之后）

上面 §2.2 的表来自"读代码"的推断；**做完一次真实标删后，实测改了两条结论**，以本节为准：

1. **归档列举本身就排除已删文件**：对 7 篇执行 `POST /api/depot/delete` 后，
   `GET /api/kb/rez_pkg/depot/list?rel=Rez_pkg` 的条目数 **33 → 29**，那 7 篇**直接不在列表里**。
   → 所以"用 `action=delete` 判断状态"这个前提**不成立**（列表根本不返回它们）：
   `depot_map.is_deleted_state()` 与 `list_tree(live_only=True)` 目前是**冗余但无害的保险**（建议保留）。
2. **已删文件的 `depot/file` 读不到**：`GET …/depot/file?rel=<已删>` 回 **502**，
   内层 depot 是 **410**「该版本已删除…」（blob 与历史保留，`rev=0` 不再可读）。
   → `notepad_read` 的"已删不兜底"实际上**是靠读失败兜住的**（而不是靠我那条 action 判断）。
   结论对，但不是靠设计的那条机制 —— 这点必须记下来，免得以后有人以为 action 判断在起作用。

**清旧行：2026-10-04 已收尾**，修法分两步（第一次只修了一半，第二次才真干净）：

- **词法侧**（`search_docs` / `search_fts`）**早就在跑**：`_kb_sync_one` 阶段 2 之后那段
  "归档里已不存在 → `_drop`"就绪（`known` = 索引行，`alive` = 本轮 live 列举；目录没列完
  `stopped_early` 时**不判删除**，免得误删还没比对到的行）。所以标删那 7 篇后，词法行确实没了。
- **向量侧**（`vec_docs` / `vec_chunks`）**当时没跟着删**，于是"搜得到、点开打不开"其实还在：
  实测 `rez_pkg` 的 `vec_docs` 里 4 篇已删文档的向量仍在，`last_embedded_at` 停在 2026-10-02
  —— 因为**嵌入那趟只由 `tools/vec_rebuild.py`（CLI）或显式重嵌触发**，可能几天不跑一次。
- 已修（见 §2.4）。

### 2.4 收尾修法（2026-10-04 实测通过）

1. **`_drop` 两侧同删**（一个字节级的前提修正）：它以前只删 `search_docs`/`search_fts`，
   向量留给"下一次嵌入"清 —— 把那趟可能很久不跑的事实摊开后，"行删了、向量还在"
   是这类清除永远不彻底的真根因。现在 `_drop` 顺手调 `search_vec.drop_doc`（连带把
   **内存块向量缓存**标脏），所有 7 处调用方（笔记消失 / 代码消失 / 删库 / kb 清旧行 …）一并受益。
2. **`search_vec.purge_orphan_vec()`**：摘掉"没有对应词法行"的向量行（`_pending_docs` 里
   本来也做，但只在嵌入那趟）；抽成函数，让周期性兜底也能调它。
3. **`search_index.purge_orphan_index()`**：一次清两类残留 —— ① **知识库本身已删**的词法行
   （`knowledge.delete_base` 只清 `knowledge_*` 三张表，索引不在其内，而这些行**再没有任何
   机会被重算**）② 上面的向量残留。挂在**kb 兜底 tick**（300s）与**启动预热**上，
   `kb_bases()` 为空时直接返回（沿用"空扫描绝不清理"护栏）。
4. 实测：临时库上验三种形态（孤儿库 / 词法行已摘的向量残留 / 正常行不受牵连）→
   `purge_orphan_index() == {"kb": 1, "vec": 1}`；线上库核过 **`vec_docs` 无词法行 = 0、
   `vec_chunks` 无对应文档 = 0、已删文档一行不剩**（词法行 53 / 向量行 45 一并对齐）。


> 版本库里的"删除"是一个**状态**：文件数据（blob / 历史版本）**仍在**版本库里，
> 但**不应建立索引**；已经建过的索引**应该被删除**。

拆成三条可验收的行为：

## 3. 目标行为（需求方的模型）

- **B1 归档侧**：源端文件消失 → 归档里对应条目的状态变成"已删"（`action=delete` 一类），**blob 与历史保留**。
- **B2 索引侧（新增不再收）**：`list_tree` 必须**过滤掉已删状态**的条目，或把状态透出给索引；索引不得为它们建行。
- **B3 索引侧（旧行要清）**：已经在索引里的"已删"文件，其行必须被**移除**（而不是靠重建自然消失 —— 重建也是从同一份列举来的，若 B2 没做，重建后照样在）。

## 4. 修法（三步，含护栏）

### 步骤 A：`depot_map` 透出/过滤状态 + 补删除能力

1. `list_tree` 的返回项**加上** `action` / `pending` / `excluded` 字段（现在被丢掉）；
2. 新增 `list_tree(live_only=True)` 之类的过滤（或由调用方判断），**默认排除** `action == "delete"` / `excluded == True`；
3. 新增 `delete_file(conn, kb_name, *, rel, description="")` —— 调 `POST /api/depot/delete`
   （`{paths:[depot_path(info,rel)], description}` + `ws` 查询参数；契约见
   `lugwit_baidu_netdisk/web_server.py::api_depot_delete`）。
   ⚠️ dir 模式下该端点会**真删镜像里的活文件**（服务端注释写明"否则拉取端会把已删笔记复活"）。

### 步骤 B：同步器传播删除（`workspace_sync._scan_kb`）

在每轮扫描的"走完 `root`"之后加一段陈旧清理：

```
seen = 本轮见到并处理的 rel 集合
stale = [rel for (kb, rel) in _synced if kb == kb_name and rel not in seen]
```

**必须先过三道护栏，缺一不可：**

1. **空扫描绝不清理**：`len(seen) == 0` → 直接跳过（工作区根一时读不到 / 盘掉线 /
   权限异常时，否则会把整个 kb 归档标记删除 —— 这是最危险的失败模式）；
2. **只清理本 kb 且曾由本同步器上传过的**：即必须在 `_synced` 里（工作区里手工新建、
   从未同步过的文件**绝不能**碰）；
3. **首轮只记日志（dry-run）**：新增 `L_NOTEPAD_WS_PRUNE`（`0` 关 / `1` 真删 /
   缺省或 `dry` 只记"将删除 N 个"到日志与同步历史），**先跑一天看日志**再开真删。

每删一个：调 `depot_map.delete_file` → 成功才从 `_synced` 移除；失败**保留状态、下一轮重试**，
并 `record_upload(... ok=False)` 记进同步历史。

### 步骤 C：索引侧清行（B2 + B3）

- 建/更新索引时**跳过** `action` 为删除状态的条目（B2）；
- 加一次"陈旧行清理"：索引里存在、但本轮列举（live only）里没有的 kb 行 → 删除（B3）；
- 顺手把 `search_index` 里"文件消失不删行"的同类问题一并处理，避免下次换个入口又踩。

## 5. 实施情况（2026-10-04 收尾）

| 步骤 | 状态 |
|---|---|
| A 归档映射透出/过滤状态 + `delete_file` | ✅ `list_tree(exts=…, live_only=True)` + `is_deleted_state()` 已到位（实测**冗余但无害**，见 §2.3：列举本身就排除已删项）；`delete_file` 未加 —— 手工用 `POST /api/depot/delete` 已够（见 §5.1） |

| C-B3 索引侧清旧行 | ✅ 词法侧早就在跑（§2.3）；**向量侧 2026-10-04 补齐**（§2.4），线上库已核到 0 残留 |
| B 同步器传播删除（`workspace_sync`） | ❌ **明确不做**（见 §6 第 5 条：多机各有工作区，"本地没有" ≠ "该删共享归档"） |

### 5.1 删除这一步怎么走（当前口径）

删除**只显式做**，入口是 depot 的 `POST /api/depot/delete`（带 `ws` 参数、认 **cookie
`lugwit_token`**——该端点读 cookie 而不是 Authorization 头，实测踩过 401）。
动作前先 `notepad_read` 拿 `meta.note` + `lugwit-note-history`（谁、什么时候、为什么改的，
见另一篇计划 §3.4），看清了再删。kb 路由上的显式删除入口（`/api/kb/{kb}/depot/delete`
薄包装）**未做**，需要时再补。

## 6. 不要做的事

- ❌ 不要直接删版本库里的 blob（`delete` 端点本身就是"标记删除、blob 保留"，语义正确）。
- ❌ 不要用"全量重建索引"来掩盖问题：重建仍从同一份列举来，B2 没做照样复活。
- ❌ 不要在 `len(seen) == 0` 时清理（见 §4 护栏 1）；索引侧的 `purge_orphan_index` 同理，
  `kb_bases()` 为空就返回。
- ❌ 不要把"工作区手工新增、从未同步过"的文件当成陈旧项清掉（见 §4 护栏 2）。
- ❌ **不要做"本地删 → 让同步器去归档标删"**（步骤 B）：同一个知识库在**多台机器**各有工作区，
  本地没有某文件**不能**推出"该从共享归档删除它"——那会互相踩掉别人刚传的文档。
